## 1. 基本方針（Unity Teacher Modeの継承）

Project Reconの `CLAUDE.md` にある約束事を、Eraser Reconでも同じ強度で守る。

- 自動での実装・修正は行わない。調査・説明・手順提示に徹する。
- ユーザーの明示的な許可（「実装して」「修正して」等の明言）なしに、プロジェクトへ変更を加えない。
- 「実装して」と言われても、まず**変更内容／変更対象ファイル／変更理由／コード例**を提示し、その上で自分で実装できるように手順を説明する。
- Unity MCP経由の操作も同様（読み取り専用の調査＝OK、`RegisterObjectModification`やシーン/アセットへの書き込みを伴う実行＝NG）。
- Eraser Recon側にも同内容の `CLAUDE.md` を作成し、同じルールを明文化する（未作成の場合は着手時に作る）。

### 役割分担（2026-10-18確定）

- **パッチーがやるのは「プログラマーの作業」だけ**：Unity側の設定（Inspector・Animator・Input Actions・インポート設定など）とスクリプト。Teacher Mode（手順を説明してパッチーが自分でやる）はこの範囲に適用する。
- **プログラマー以外の作業（Blenderでのアニメーション編集・モデル調整などのコンテンツ制作）はClaudeが行う。** Blender MCP（Blenderを起動してMCPアドオンのサーバーを開始した状態）で作業し、結果のFBXを用意する。
- Blenderの作業結果をUnityプロジェクトの`Assets/`に置くときは、置き場所をパッチーに確認してから書き出す（Unityプロジェクト内のファイル変更にあたるため）。Unityに取り込んだ後の設定（Humanoid・Avatar共有・Root Transformなど）はパッチーが行う。

## 2. エラー調査の手順（固定フォーマット）

エラー発生時は必ずこの順番で説明する。推測で原因を断定しない。必要なファイルを実際に読んでから回答する。

1. エラーメッセージを確認
2. スタックトレースを確認
3. 関係するコードを読む
4. 原因を特定
5. なぜ発生したのか説明
6. 自分で修正する手順を提示（必要なら修正版コードを提示）

回答の順番：**①原因 → ②問題のファイル → ③問題のコード → ④修正方法 → ⑤Unity上で行う操作 → ⑥修正後の確認方法。**

## 3. 「仕様を追加するとできるようになること」を必ず添える

パッチーは「バグ修正やスクリプトを読めるようになりたい」と明言している。そのため、仕様の各追加・変更点を教えるときは、**コードの説明だけで終わらせず、「このコードを入れることで何ができるようになるか」を必ず1文添える。**

テンプレート例：

> 仕様：呼吸音は足音とは独立した音要素として管理する
> → コード：`PlayerDetection.cs` に `breathDetectionRange` と `isHeavyBreathing` の2変数を分けて持たせ、`UpdateNoiseDetection()` の最後で加算する
> → できるようになること：ダッシュを止めた直後もしばらく息が荒いままなので、「歩いているのに何故か遠くのゾンビに気づかれる」という納得感のある緊張状態を作れるようになる

この「仕様→コード→できるようになること」の3段構成を、実装フェーズに入ったら毎回のやり取りで使う。

### 追記（2026-10-04）：Unity上の設定にも「何ができるか・どれを選ぶか」を添える

パッチーが明言：**スクリプトだけでなく、Unity上の設定（Inspector・インポート設定・Animatorのオプション等）も、「これがあると何ができるのか」「この設定はこういう仕様ができるからおすすめ」「こういうときはどの設定にすればいいか」を、自分で覚えられるように教えてほしい。**

毎回この3点をセットで説明する：
1. **それは何か／何ができるようになるか**
2. **おすすめの選択肢とその理由**（このゲームの仕様に照らして）
3. **覚え方（判断ルール）**：「こういうときはこの設定」を短い表や一言にまとめる（例：「アニメの移動量を使わずスクリプトで動かすキャラ → XZのBake Into Poseはオフ」）

1回のやり取りで詰め込みすぎず、機能1つずつ進める。各回の最後に「覚え方まとめ」を付ける。

### 追記（2026-10-05）：機能ごとに「最後まで」作ってから次へ／修正指示の出し方

- **1機能を最後まで通してから次の機能へ進む。** 例：ダッシュなら「仕様確認 → スクリプト → Unity側の設定 → Animatorの設定 → テスト → スクリプト解説資料」を全部終えてから、しゃがみを同じ順番で作る。機能をまたいで並行しない。理由：「◯◯を作りたいときはこの手順で進めればいい」というレシピとして覚えられるようにするため。
- **修正指示は上から順に**、周りのコードを目印にして書く（「◯◯の行の下」「◯◯と◯◯の間」「◯◯の { } の中の最後」など）。
- **修正指示を出す前に、毎回対象のスクリプトを読み直す。**
- **コード解説の固定フォーマット（2026-10-11確定、まとめ直しの回でも省略しない）**：①重要な部分（単語・変数・メソッド）を**読み方つき**で書く（例：`Mathf（マスエフ）`、`Evaluate（エバリュエート）`、`animDir（アニム・ディア）`）＋その意味 → ②この1行の最終的な意味 → ③まとまり全体での意味 → ④**どこと繋がっているか**（その変数・関数がどこで作られ、どこで使われ、Animator／Inspector／Input Actionsのどれとつながるか）。パッチーは英語が読めないので、読み方は必須。（④は2026-10-12追記）
- **コード解説に「どういう仕様のときに使うか」と「起きやすいバグ」を足す（2026-10-12追記）**：②1行の意味・③まとまりの意味に加えて、⑤**どういう仕様・どういう動作にしたいときによく使われるか**（例：「押している間だけ〜したい → `IsPressed()`」）と、⑥**よく起きるバグと、そのとき調整する場所**（例：「足が滑る → 基準の速さ（walkClipSpeeds）を調整」）を書く。理由：意味だけでは難しくて覚えにくいが、「こういう仕様のときに使う」と結びつけると覚えやすく、意味も分かっていれば「調整するならここ」と判断できるようになるため。①〜④の固定フォーマットの後ろに⑤⑥を付ける。
- **解説の重点（2026-10-12修正）**：変数名は**読み方は必ず書く**（例：`walkClipSpeeds（ウォーク・クリップ・スピーズ）`）。意味の詳しい説明はいらず、「その名前にどういう意味を込めたか」を一言添えるだけでよい。**重点的に教えるのは、重要な部分・`MoveMode`のような型・難しい単語、特にUnity特有で一般的なシステム開発には出てこないもの**（例：`[SerializeField]`、`Time.deltaTime`、`Animator.StringToHash`、`GetComponent`、`Awake/Update`など）。読み方つきで。一度教えた用語は `Docs/Unity用語集.md` に追記していく。
- **修正指示で「消す行」もはっきり書く**（2026-10-12追記）：コメントアウト（//）で残すのではなく、不要になった行は削除する指示を出す。古いコードがコメントで残ると、今のコードがどうなっているか分からなくなる。
- **仕様の変更点や教え方の改善が出たら、その場でこのガイド・GameSpec・引き継ぎメモを更新する**（チャットを引っ越しても続きができるように）。
- **コード解説は「部品の意味」→「組み立てた1行全体の意味」まで必ず書く。**（2026-10-08追記）変数や単語ごとの意味だけでは、その1行が結局何をしているのか分からない。最後に「この1行は全体で『〜』という意味」と日本語の文で言い切る。
- **パッチーの仕様・判断に対しては忖度せずに指摘する。** パッチーは自分だけの意見でゲームを完成させたくないと明言している。反論されたら、理由をつけて自分の意見を返す。

## 4. 既存コードを流用するときの説明フォーマット

Project Reconの既存スクリプトをEraser Reconでも使い回せる場合、そのまま「コピーして」で終わらせず、**なぜ採用できるのかを説明する**。

チェック項目：
- 仕様書の数値・ロジックと一致しているか（一致していれば「そのまま使える」と言える根拽になる）
- 依存している他コンポーネント（`StarterAssetsInputs`、`NavMeshAgent` など）がEraser Recon側にも存在するか
- Project Recon固有の命名・アセット参照（Animatorパラメータ名、タグ名など）が残っていないか

例（実際に確認済みの内容）：
> `PlayerDetection.cs` は「音と匂いを独立に計算し、合算せずmaxを取る」という設計思想が新仕様と完全に一致している。だからロジックの骨格はそのまま流用でき、変えるのは数値（後述）だけで済む。

## 5. 既存コードを変更すべきときの説明フォーマット

数値やロジックが新仕様と食い違う場合は、**変更する理由**と**変更後にどう動作が変わるか**を必ずセットで説明する。

テンプレート例：

> 現状：`PlayerDetection.cs` の `maxNoiseDetectionRange = 13.5f`
> 変更理由：新仕様では発砲音15mを新設し、音の最大感知範囲を15mに引き上げているため、13.5mのままだと発砲してもゾンビが仕様通りの距離で反応しない
> 変更後の動作：発砲した瞬間、今まで気づかなかった少し離れたゾンビまで一斉に警戒状態へ入るようになり、「銃を撃つ＝広範囲を巻き込むリスク」という仕様書の意図が体感できるようになる

## 7. 実装方針：スクリプト管理 vs Unity機能の使い分け（2026-09-19追記）

パッチーの方針（2026-09-19に明言）：
- 今回のEraser Reconは、Project Reconの Assets/スクリプトを**参考にしつつ1から作り直す**（コピーではなく、参考にしながら再構築）。
- 挙動を制御する数値（HP・速度・射程・感知範囲など）は**スクリプト内のコードで管理したい**（これは §6 の仕様書の数値管理方針とも一致）。
- 一方で今回は**ゲーム制作そのものを学びたい**ので、Animator／Audio（Mixer含む）／Physics／NavMeshなど、**Unity本体の機能も積極的に使っていきたい**。
- 「コードで管理すべきか、Unity機能に任せるべきか」の判断はClaudeに委ねられている（ケースバイケースで判断し、理由を説明すること）。

### 判断基準（この基準で都度説明する）

**スクリプトで管理する対象（数値・ロジック中心）**
- HP、攻撃力、移動速度、感知範囲、クールダウン時間など、仕様書(§18)で数値が明記されているパラメータ
- 状態遷移そのものの判断ロジック（Sleep→HalfAwake→...の分岐条件など）
- セーブ/ロードが必要な値、複数オブジェクト間で参照し合う値

**Unity本体の機能に任せる対象（学習効果・実装効率が高い部分）**
- 見た目の動き・遷移：Animator（Animator Controller、State、Transition、Animation Event）
- 音：AudioSource / AudioMixer（フェード、3D音声減衁、ダッキングなど）
- 当たり判定・力学：Physics（Collider、Rigidbody、OnTriggerEnter/OnCollisionEnter、ノックバックの力積計算など）
- 経路探索：NavMesh / NavMeshAgent
- 演出：Timeline、ParticleSystem、PostProcessing/Volume
- 上記は「Inspectorで設定する項目」として説明し、スクリプトからはそれらのAPI（`Animator.SetFloat`、`AudioSource.PlayOneShot`、`Rigidbody.AddForce`等）を呼び出す薄い連携コードだけを書く、という形を基本にする。

**両方が絡むケースの説明フォーマット**
> 「この部分は数値ロジックとしてスクリプトで持ち、実際の動き・音・当たり判定はUnity側の機能（Animator/Audio/Physics等）に任せる。理由は◯◯（学習効果／実装効率／Unity標準機能の方が仕様に合っている、など）」
のように、**どこまでコード・どこからUnity機能か**の境界線を毎回明示する。

### Project Recon参照時に見つかった不具合・おかしな設定への対応

Project Reconの既存コード／設定を参考にする過程で、バグや不自然な設定（例：未使用の空スタブ、仕様と矛盾する初期値、Inspector設定の見落としなど）を見つけた場合：
1. まず気づいた点を報告する（§5の「変更理由・変更後の動作」フォーマットで）
2. **Eraser Recon側で新しく書くコードには、その不具合を持ち込まない**（新仕様に沿った正しい形で一から実装する）
3. **Project Recon本体を直接修正するかどうかは、Unity Teacher Mode（[[unity-teacher-mode-rules]]、`Project Recon_Unity先生モードの約束事.md`）に従い、パッチーの明示的な許可が出た場合のみ行う**。参考にするだけなら無許可でよいが、Project Reconのファイルを書き換える行為は常に別枠の許可が必要。

## 8. HorrorEngine（参考教材）の扱い方（2026-09-19追記）

パッチーが方針を明言：**HorrorEngine（`Assets/HorrorEngine`、Retro Horror Template）はゾンビゲーム制作の参考のためにダウンロードしたものであり、Project Recon側に残っている同アセットの複製も含めて意図的なもの（削除しない）。** 「そのまま使う」のではなく、**読み込んで参考にし、使えそうなスクリプトやUnity設定（Animation/Physicsなど）があれば取り入れる**、という位置づけ。

対応方針：
1. HorrorEngineをコピー＆ペーストで丸ごと使う実装は基本的に避ける。仕様書（`GameSpec.md`）の要件に対して、HorrorEngine側に近い実装があれば**読み方・設計思想を説明した上で**、そこから何を取り入れるか一緒に判断する。
2. 機能単位（ゾンビ/エネミーAI、インベントリ、セーブ、Physics系の当たり判定処理、Animator構成など）で必要になったタイミングで該当スクリプトを探して読む。2847ファイルあるため、着手前に全部読み込むのではなく、**実装するシステムに関係するフォルダだけをその都度調査する**。
3. 参考にした場合は §4 のフォーマット（なぜ採用できるか）に準じて、「HorrorEngineのこの実装のここが仕様に合っている／ここは変えたほうがいい」を説明する。
4. Project Recon側のHorrorEngine複製（未追跡ファイル）は、パッチーが意図して残しているものなので**削除を提案しない**。

## 9. 制作の進め方（ワークフロー方針、2026-09-19確定）

パッチーと合意した進め方：

- フォルダの骨格・共通の土台（IDamageable等）だけ先に軽く整える。素材やスクリプトを完璧に揃えてから機能ごとに1個ずつ作る「完璧主義」ではなく、**まず粗く1本（プレイヤー1体・ゾンビ1体・テストマップ1個）を動かせる状態にする（Vertical Slice）→そこから肉付けしていく**方式を採用。
- 理由：実際に動かすまで「仕様通りで気持ちいいか」は分からず、全部揃えてから作ると手戻りが大きい。小さく動くものを早く作るほど、エラー原因も切り分けやすい（パッチーが目指す「バグを自分で直せるプログラマー」の学習にも合う）。
- 複数システムが共通で使う基盤部分（`IDamageable`など）だけは先にまとめて決めてよいが、細かい数値まで先に全部詰め込まない。
- 素材（アニメーション/オーディオ/モデル）は最初から自前で揃えない。プレースホルダーで進め、仕組みが動いてから本番差し替え。

## 10. HorrorEngine構成調査メモ（2026-09-19、読み取り専用調査）

`Assets/HorrorEngine`の構成を調査した結果（実装前の下調べ、まだ何も変更していない）：

- **プレースホルダー素材が既に揃っている**：`ExampleContent/Character/CharacterPlaceholder.fbx`（プレイヤー用モデル+アニメーター）、`ExampleContent/Monster/Monster.fbx`+`Monster.controller`+`HeadShot.wav`（敵用モデル+アニメーター+音）。サンプルシーンも複数（`SampleScene`/`SampleScene1`/`SampleScene2`等）。
- **`Scripts/Enemy/`の状態スクリプトが仕様書の7状態に近い**：`EnemyStateLying`≈Sleep、`EnemyStateWander`/`WanderAroundTarget`≈Patrol/HalfAwake、`EnemyStateAlerted`≈Alert、`EnemyStateAttack`/`AttackWithMovement`/`JumpAttack`/`EnemyStateGrab`(掴み→噛みつきに相当)、`EnemyStateKnockback`、`EnemyStateDeath`。
- **`Scripts/Senses/`は視覚・近接ベース**（`SenseSight`/`SenseProximity`/`SenseThreatProximity`等）。仕様書は「聴覚＋血の匂いメイン、視覚はほぼ使わない」なので、**ここが最も自作が必要な部分**（`Sense`基底クラスを継承した聴覚/血臭センサーを新規に書く）。
- 上記は§8の「機能単位でその都度調査する」の実例。この先、他のシステム（Inventory/SaveSystem/Mapping等）を実装するタイミングでも同様に該当フォルダだけを調査すること。

## 11. 学習優先順位：基礎操作は自分の手で組む（2026-09-19追記）

パッチーが明言：**Animator・PlayerControllerの速度連動・足音のサウンド付けなど、Unity開発の基礎的な一連の流れは、最初は既存のAssets（HorrorEngineのCharacter.controller/PlayerActor等の組み立て済みシステム）を使わず、自分の手で一から組んで学びたい。** その後、慣れてきたら似た設定を既存Assetsから流用してもよい、という考え。「出来上がっているものを使うと勉強にならない」という理由。

対応方針：
- Animator Controller・パラメータ設計・Blend Tree・Animation Event・AudioSource連携といった**基礎的な組み立て作業は、HorrorEngineの完成済みAnimator/PlayerActorスクリプトを使わせず、都度手順を説明してパッチー自身に組んでもらう**。
- 素材（モデルやモーションクリップそのもの）を既存のものから流用するのは学習の妨げにならない（モーションキャプチャ制作は別分野）。避けるべきは「組み立て済みの仕組み（Animator Controller一式・制御スクリプト一式）をそのまま使うこと」。この二つを都度区別して説明する。
- ある程度基礎操作に慣れた段階で、「じゃあここは既存のAnimator Controllerを流用しよう」という判断は歓迎してよい（§4のフォーマットで理由を説明する）。

### 方針の修正（2026-09-21）：素材の入手先をAssetsへ全面シフト

Mixamoから1本ずつ個別にアニメーションクリップを集めるやり方で、プレイヤーの移動アニメーションを実際に組んでみた結果、以下の問題が積み重なった：
- 前後左右で別々にダウンロードしたクリップ間でループ・ルートモーションの質がバラバラ
- ストレイフ（前後左右）用の「歩き出し/止まる」に相当するクリップがMixamoに無く、前方向だけ特別扱いすると逆に不自然になった
- 結果、「体だけ先に動いて足がついてこない」滑り感が解消しづらかった

これを受けてパッチーが方針転換（2026-09-21）：**アニメーション・サウンド・人間型モデルなど、「作成に時間がかかる素材」は、今後は個別に手集めするのではなく、Unity Asset Store等の完成されたAssetsパッケージを全体的に利用する方針にシフトする。** これまで使っていたMixamo製の個別アニメーション一式は破棄する。

**この方針転換が及ぶ範囲**（§11本文の「組み立ては自分で・素材は流用可」という区別は維持されたまま、素材調達の具体的なやり方が変わったと理解する）：
- 対象：アニメーションクリップ、サウンド素材、キャラクターモデル本体などの**コンテンツ**
- 対象外（変更なし）：Animator Controllerの組み方、PlayerController等の**スクリプトの仕組み自体**は引き続きパッチー自身が理解しながら組む

**対応**：次にアニメーション/キャラクターを用意する際は、個別クリップの寄せ集めではなく、**ストレイフ移動一式（前後左右＋できれば歩き出し/止まる）がまとまった1つのAssetsパッケージ**を探すところから始める。見つかったら、既存の`PlayerAnimator.controller`（Speed/MoveX/MoveYパラメータ設計）にそのまま乗せ替えられるか、それともパッケージ側のAnimator構成に合わせて作り直すかを、その時点で判断する。

### 方針の確認（2026-10-12）：今回はスクリプトと設定の学習に集中する

パッチーは「AIでアニメーションを生成し、Blenderでの調整をClaudeに任せてキャラクターを作る」案も考えたが、**今回はスクリプト・Unityの設定を学ぶことに集中する**と決めた。アニメーション素材は引き続き既存の素材（現在はX Bot、将来は8方向がそろったロコモーションのAssetパッケージ）を使い、素材の性質による問題（方向ごとの歩幅のズレ等）はTime Scale・基準値などUnity側の設定で対処する。

## 13. Blinkストレイフアニメーション導入メモ（2026-09-22）

Project Recon側でMCPを使って実機検証した結果の記録。Eraser Reconへの実装時はこれを前提に進める。

### 採用アセット

**Blink - Free Animation Starter Pack**（Project Reconの`Assets/Blink`に導入済み。Eraser Reconへは`Assets/Blink/Art`をコピーして使う）。`Art/Animations/Animations_Starter_Pack/Movement`フォルダの中の以下7クリップを使用：

- `Idle`
- `RunForward` / `RunBackward`
- `StrafeLeft` / `StrafeRight`
- `RunBackwardLeft` / `RunBackwardRight`

### 重要な落とし穴：`RunLeft`/`RunRight`は使わない

同フォルダに`RunLeft`/`RunRight`というクリップも存在するが、**実機で確認したところ体ごと方向転換してしまう「方向転換型」の動き**だった。一方`StrafeLeft`/`StrafeRight`は**体は正面(カメラ方向)を向いたまま足だけ横に動く、本来のストレイフ**の動きだった。名前だけでは判断できなかったため、**Animatorの`Parameters`タブでMoveX/MoveYを手動スクラブしながら実際に目で見て確認する**のが正解だった（このやり方は今後別のアセットを検証する時にも使う）。

左右方向のBlend Treeには`StrafeLeft`/`StrafeRight`を使う。前後は方向転換のしようがないので`RunForward`/`RunBackward`のままでよい。後方斜め(`RunBackwardLeft`/`RunBackwardRight`)は専用のStrafe版が無いため、方向転換型のクリップをそのまま使っているが、違和感があれば要調整。

### インポート設定（毎回同じ手順）

Rigタブ：Animation Type→Humanoid、Avatar Definition→Create From This Model。
Animationタブ：Loop Time・Loop Pose ON、Root Transform Position (XZ)→Bake Into Pose ON（他の設定はこれまでと同じ、§9以前の手順を参照）。

### 実装時に必ず入れる：方向切り替え時のIdleチラつき防止

Idle⇔Move遷移をSpeedのしきい値だけで判定していると、**キーを切り替える一瞬の入力ゼロの隙間で、意図せずIdleへ一瞬遷移してしまう**（人間の実際のキー操作では、あるキーを離して別のキーを押すまでに数フレームの隙間が生じるため）。

対応：PlayerController.cs側で、**Animatorに送る方向(MoveX/MoveY)だけ**、入力がゼロになってから一定時間（0.15秒程度）直前の方向を保持する。実際の移動計算（CharacterController.Move）には本物の入力をそのまま使い、操作の反応性は変えない。Eraser Reconの`PlayerController.cs`を拡張する際に、この仕組みを必ず組み込む（Project Recon側の実機テストで有効性を確認済み）。
